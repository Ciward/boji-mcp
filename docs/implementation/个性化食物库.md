# 个性化食物库 v0.2.0

个性化食物库保存用户常见食物和餐厅菜品的可复用基线：名称与别名、品牌/餐厅、规格或做法、参考份量、营养、核验来源及修订历史。`boji_get_context` 返回 `schema_version: 2` 和 `workflow_version: "0.2.0"`。npm 包版本为 `0.2.0`；这份契约不声明任何远程部署状态。

## 每餐使用规则

1. **先读 context，再查库。** 每次记录一餐，先调用 `boji_get_context` 获取当前日期、时区、schema/workflow 版本和本次写入可用的 `request_key`。然后为每种候选食物调用 `boji_search_food_library`；不要跳过搜索直接创建基线。
2. **逐项核对是否同一商品/菜品。** 搜索命中后按需调用 `boji_get_food_library_item` 读取当前条目，核对同一餐厅或品牌、`variant`（规格/做法）、`serving_label` 和 `amount_g`（参考份量）、`verified_at` 与 `source_urls`。名称相似不足以确认匹配；不同餐厅、不同规格、不同做法或参考份量不可直接复用。
3. **匹配才采用基线。** 只在身份和份量依据相符时使用库中营养。将每个已知营养值按本次整份份量与库中参考份量的比例换算；某字段无法可靠换算时保留 `null`，并说明原因。`amount_g` 记录本次整份重量，`nutrients` 写换算后的本次整份值，`consumed_fraction` 表示实际吃掉的比例，交给服务端乘一次。例如基线为 280 g、本次端上 350 g，则可按 350/280 换算已知营养，再由服务端乘本次食用比例。
4. **无命中或不匹配时，由宿主检索可靠来源。** 优先查产品标签、品牌官方营养资料或餐厅官方菜单。把研究摘要写入条目的 `notes`，记录 `source_urls` 和实际核验时间 `verified_at`；来源未给出的营养字段可为 `null`。照片估算只能作为本次餐食的视觉估算，不能冒充官方标签或菜单数据。找不到可靠资料时，不把照片数字保存成已核验的官方基线。
5. **有本次授权即可自然维护库。** 当用户已授权当前饮食记录工作流进行相应写入，稳定且有依据的新条目可随本次餐食自然新增；有新核验信息时可先读取再修订现有条目，无需每餐额外确认。只处理本次餐食涉及的条目；不扫描或自动学习所有历史餐食。食物库归档/删除仅在用户明确要求时执行。
6. **把引用和快照一起保存。** 使用匹配基线时，餐食 `items[]` 可带 `food_library_ref: {id, version}`，且引用必须是有效的最新活跃版本。餐食营养本身保存为本次快照；日后库条目更新或归档不追溯更改旧餐。修改旧餐时按原有出现次数一对一保留相同的老引用是允许的，不能复制旧引用到新增食物项；新增或更换引用必须重新核对当前活跃版本。
7. **遵守版本和幂等。** 写库前取得当前版本；更新、归档、恢复传 `expected_version`。冲突后先重新读取并合并。每项独立写操作使用自己的 `idempotency_key`；超时重试复用原 key 和完全相同的内容。只有收到 `persisted: true` 才报告保存成功。

MCP 本身不执行 Web 搜索或模型推理，也不自动将每一顿历史餐食吸收到食物库。宿主负责识别、检索、来源判断和份量换算；Boji 负责受权限约束地检索与持久化。字段及 REST/MCP 参数详见 [API 契约](API契约.md)。

## 通用宿主可复制提示词

```text
你是我的饮食记录助手，Boji 是持久账本。开始每次餐食记录时先调用 boji_get_context，再对本次识别出的每种食物调用 boji_search_food_library。

对每个命中，读取需要复用的条目并核对 restaurant_name（同一餐厅/品牌）、variant（规格与做法）、serving_label、amount_g、verified_at 和 source_urls。只有确认为同一商品/菜品且份量可比时才复用。把基线按本次端上整份的份量换算成整份 nutrients，amount_g 填本次整份重量；consumed_fraction 只描述吃掉的比例，由 Boji 服务端乘一次。不可比或无法换算的营养字段填 null 并说明。

无命中或不匹配时，由宿主检索标签、品牌官方资料或餐厅官方菜单等可靠来源。找到资料后，把简短研究摘要、source_urls 和核验时的 ISO-8601 verified_at 一并保存；来源无法确认的营养字段为 null。照片估算可以用于当前 meal item，但绝不能标成官方标签/菜单值。找不到可靠来源时，不要把照片估算伪装成已核验基线。

当当前记录任务已获准写入餐食及其相关食物库时，可自然新增可靠基线或读取并修订同一身份条目，无需每餐再问一次；仅处理本次餐食涉及的条目，不自动学习所有历史餐食。食物库归档/删除只有在我明确要求时才执行。遇到同身份活跃条目先读取并更新，不创建重复项。

使用基线时，在 meal.items 对应项写入 food_library_ref: {id, version}。新建 meal 或新增/更换引用必须使用当前活跃的最新版本；更新历史 meal 时原样保留既有老引用和既有营养快照，不用当前食物库重算。遇到失效引用或版本冲突，先读取最新版、核对后再提交。

每个独立写操作使用独立 idempotency_key；超时重试时复用相同 key 与完全相同 payload。版本冲突时读取当前版本并合并，不能盲目覆盖。仅当工具回执 persisted:true 时说已保存。MCP 只负责数据操作，不会替你搜索网络或做模型推理。
```

## Web、历史和备份

Web 食物库支持搜索和筛选、查看条目、编辑、查看版本历史、归档和恢复。相同身份的活跃条目不可重复创建；归档不清除历史，恢复也会检查活跃条目冲突。

食物库内容及 `food_library_history` 会进入 JSON 导出；SQLite 在线备份包含食物库表和历史表。条目修改或归档不会更改既往 meal 快照。回收和版本历史是 Boji 账本内的操作，不会同步删除外部 Apple Health 测量数据。
