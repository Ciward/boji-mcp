# ChatGPT 接入与部署

当前 npm 包版本为 `0.2.0`；个性化食物库的数据 schema 为 `2`，工作流为 `0.2.0`。本文说明连接、配置和验证方法，不记录任何未经本次核验的线上部署结果。

## ChatGPT 手动接入

在当前账户的自定义 MCP/插件连接入口添加服务，填写完整 HTTPS `/mcp` 地址并选择 OAuth。服务支持动态客户端注册（DCR）和 PKCE S256；未启用 CIMD，若界面要求选择注册方式，选择动态注册。不要选择无认证，也不要把管理密码作为模型提示词或 token 发给 Agent。

OAuth 会打开 Boji 授权页。核对回调域名和所申请权限，用 Web 管理密码登录同意授权。记录餐食并维护个性化食物库需要 `health.read health.write`；只读连接仅授权 `health.read`。无需手工填写 Client Secret（动态注册的公共客户端采用 `none`）。如果账户 UI 需要预填 Client ID，先按该 UI 显示的准确回调地址注册客户端；不可猜测回调路径。官方接入依据见项目的资料来源与兼容性文档。

不要直接打开或收藏不带参数的 `/oauth/authorize` 地址；授权链接由客户端为每次连接生成。浏览器直接访问时会显示连接说明，需回到客户端重新发起连接；此时不会创建授权或登录会话。

连接后先发送：

```text
请调用 boji_get_context，告诉我服务返回的本地日期、时区、schema_version 和 workflow_version；随后只读查询今天的餐食。不要创建示例餐食或食物库条目，也不要只回答你能够调用。
```

收到真实工具回执后，再发送餐食照片或文字，并确认当前连接已获读写授权。食物库每餐工作流和通用宿主提示词见[个性化食物库文档](个性化食物库.md)。

初次授权页默认展示读写权限，显式只读连接仍受限。支持 refresh token 的宿主可在 access token 到期后续期；不要把每小时令牌到期当作必须每小时重新登录。连接过期时可用 `boji.auth` 日志区分 token 失效与 `scope_required`。只读连接增加写权限仍须用户同意授权，详见[授权契约](授权契约.md)。

## v0.2.0 可运行提示词

```text
你是我的饮食记录助手，使用 Boji MCP 作为持久账本。每次记录前先读取 boji_get_context，采用服务返回的时区、日期、schema_version 和 workflow_version。
收到食物照片或饮食描述后，先判断是新餐、同一餐另一角度、餐后剩余还是补充说明；若是已有餐，先读取当前 meal 和 version。
对本次每种食物优先搜索个性化库，并核对餐厅/品牌、规格与做法、参考份量、verified_at 和来源。只有确认匹配才使用库基线；按本次端上整份份量换算 nutrients，consumed_fraction 只由服务端乘一次。每餐规则详见个性化食物库文档。
无命中或不匹配时，由宿主检索标签、品牌官方资料或餐厅菜单等可靠来源；保存研究摘要、source_urls、verified_at。来源无法确认的营养字段为 null。MCP 不执行网络搜索或模型推理；照片估算不得冒充官方数值。
当本次餐食记录任务已经获准写入时，可自然新增或修订本餐涉及且有可靠依据的食物库条目，无需每餐另行确认；不自动学习全部历史餐食。只有用户明确要求才归档食物库条目。
meal item 的 nutrients 是本次整份营养；amount_g 仅描述本次整份重量。未知填 null，不以 0 代替。新餐或新增/更换食物库引用时使用当前活跃的最新 food_library_ref {id, version}；修订旧餐时保留原有营养快照和已有历史引用。
新建餐食调用 boji_record_meal；修正调用 boji_update_meal，并传当前 expected_version。每项逻辑写入使用自己的 idempotency_key；同次重试复用原 key 和相同内容。遇到版本冲突先回读并合并。
只有收到 persisted:true 才报告已保存；说明记录 ID、主要营养、估算局限与缺测项。汇总只包含已记录摄入，null/缺测不等于零。
```

## 本机与服务器配置

配置项：`BOJI_HOST`、`BOJI_PORT`、`BOJI_PUBLIC_URL`、`BOJI_PUBLIC_URL_ALIASES`、`BOJI_DATA_DIR`、`BOJI_TIMEZONE`、`BOJI_ADMIN_PASSWORD`。公开 URL 须为 HTTPS origin（不带路径），本机回环开发允许 HTTP。密码只通过环境配置；setup 生成随机 32 字符密码并将 `.env` 设为 0600，不写入 Git 或日志。

迁移域名时保留原域名入口、TLS 和原 Host 转发，并配置：

```dotenv
BOJI_PUBLIC_URL=https://boji.example.org
BOJI_PUBLIC_URL_ALIASES=https://legacy-boji.example.org
```

别名以逗号分隔，只能是与主域名同协议的可信根 origin。保持原管理员密码或同一 scrypt verifier，启动时不会因域名变化删除授权；缺少原 issuer 别名时会报错并保留数据。旧客户端仍可用原域名、授权码与 refresh token；新客户端使用新域名。浏览器 Cookie 不跨域自动共享，新域名 Web 首次访问需要登录。不要把反向代理的 Host 统一重写成新域名，否则旧客户端的 OAuth 发现身份会发生变化。配置在进程启动时加载，本文不承诺容器重建无停机；切流前需要独立验证并遵守当前操作的停机边界。

回滚注意：旧版本仍会在 `auth_settings.issuer` 与配置域名不同时删除全部既有授权。新版本切换主域名后，不得直接用旧二进制/镜像和旧域名启动同一迁移后数据库；仅恢复镜像或 `.env` 不是安全回滚。优先使用本版本代码保留新旧别名回切流量；如必须退回旧代码，应先停止相关写入、保留迁移后数据库并制定经验证的 issuer/数据恢复方案，不能直接覆盖或启动旧版本。

服务默认绑定 `127.0.0.1`，远程访问应通过受控反向代理或隧道转发到服务。通用 Compose 位于项目根目录 `compose.yaml`。部署前应针对目标环境核验配置、数据目录权限、域名/TLS、代理来源限制和健康检查；本文件不代替当前实例的提交、镜像、路由或健康状态核验。

设备配置：Web → 数据源 → 添加来源 → Health Auto Export，保存一次显示的 token 和接收 URL。桥接工具通过 HTTP POST JSON，并带 `Authorization: Bearer <token>`。先发送小范围数据，再查看来源接收时间和覆盖范围。详见健康接入契约。

## 验证分层

- 单元：幂等、版本冲突、null、日期、恢复、健康数据去重/单位、OAuth 负例和食物库条目校验。
- 集成：MCP 工具发现与读写权限、OAuth PKCE、食物库创建/搜索/修订/归档/恢复、餐食引用与快照、Web 修正后 MCP 回读。
- 浏览器：登录、餐食录入、食物库编辑与历史、归档/恢复、来源添加/XML 导入及手机宽度。
- 公网：针对实际目标单独验证 TLS、未授权 401、OAuth 发现和交换、工具权限、刷新令牌轮换及授权后的真实 MCP 读取。`node scripts/smoke-remote.mjs https://部署域名 .env --read-only` 为只读健康账本的冒烟流程；测试凭证须在验证后撤销。
- 宿主：当前 ChatGPT 账户连接并产生真实工具回执；只有此项通过才能称该账户宿主接入已验收。

## 备份恢复

`npm run backup` 通过 SQLite 在线备份 API 生成一致快照，包含 WAL 中已提交内容，也包含食物库及 `food_library_history`。JSON `/api/v1/export` 包含餐食、餐食历史、食物库和食物库历史，以及健康数据。备份与导出都包含私人数据，必须限制访问；授权记录包含在 SQLite 备份中，JSON 导出不包含密码或认证 token。目前为手动备份，不自动创建周期任务。

恢复前停止 Boji，并把当前数据库及相应 `-wal/-shm` 保留为回滚副本；将备份恢复到新的空数据目录，保留原时区并设置服务用户权限，再启动指向该目录的实例。不要把新主 DB 覆盖到带旧 WAL 的目录。恢复后检查 `PRAGMA integrity_check`、餐食和食物库条数、两类历史、日合计及登录；确认恢复结果后再切换流量。

## 本地大文件导入

完整 Apple Health XML 文件不通过 HTTP 发送。先用 Web 创建 `apple_xml` 来源，再在拥有数据库目录权限的服务器上运行：

```bash
npm run import:health -- --file /secure/export.xml --database /secure/data/boji.sqlite --source SOURCE_UUID --timezone Asia/Shanghai
```

CLI 先完整验证文件和每个分批，再写目标库；中断会输出 `partial`，重复执行按稳定 ID 幂等。它不接收或输出设备 token，不创建新来源，也不会把原始 XML 打进日志。

## 当前功能边界

食物库和餐食工具属于仓库中的 workflow 0.2.0 契约；具体账号的 MCP 授权、服务器部署和公网状态需要单独验证。MCP 不内置联网搜索或模型推理；已授权宿主可检索可靠标签/菜单并通过工具保存资料。自研 iOS 客户端、强制手机同步、主动任务调度、22 点报告快照、照片存储和 Boji 内部模型 API 调用不属于本文确认的功能。HTTP XML 上传仍限制为 20 MiB；完整大历史导入按健康接入契约使用本地 CLI。当前接口用于个人记录，多用户隔离尚未实现。
